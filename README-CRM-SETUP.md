# RealEstate Demo — CRM expansion

This is the **entire React/Vite website source** plus a new CRM module. The original property website, Supabase connection and listing/gallery code are retained.

## What is implemented

- Employee directory with registration, editing, active/inactive status, employee photo storage, automatically generated employee code (EMP0001 ...), and role assignment.
- Supabase Auth email/password login linked to role-specific CRM memberships. The admin interface uses client-side route guards **and Supabase RLS for newly added tables**.
- Staff workspace: only assigned leads, own follow-ups, own site visits (data restricted by RLS).
- Manager/admin: all leads, employees, booking records, reports, properties.
- Assign/reassign leads to employees; change lead stages, schedule follow-ups and save timestamped activity notes.
- Lead search, status filters, repeated-phone indicators and click-to-WhatsApp links.
- Follow-up planner with today, overdue, upcoming and an in-app notification bell (not push/SMS alerts).
- Site visit scheduling, status/outcome updates, and employee assignment.
- Bookings, amount received, outstanding balance, sales pipeline stage and Excel export.
- Reports with lead totals, bookings and employee-level lead/sales counts.
- Compact and responsive, pale-blue/navy/emerald admin UI with animated cards, mobile sidebar and normal page scrolling.
- Fixed Add Property Plot option and empty numeric fields; fixed optional date submission in website Contact form.

## Required Supabase setup — do this BEFORE logging in

**Back up the existing Supabase database first.** The database migration adds tables and RLS policies; it changes permissions on the existing `leads` table.

1. In Supabase, open **SQL Editor** for the correct project.
2. Review and run `supabase/migrations/20261102_crm_foundation.sql` **once**. This is not executed automatically by Vite and must be reviewed against your current schema.
3. In Supabase **Authentication → Users**, locate your existing admin account's UUID. Make sure the account exists with email/password.
4. Run the following in SQL Editor after replacing the sample value with that admin's **real Auth user UUID**:

   ```sql
   insert into public.crm_memberships(user_id,role)
   values ('YOUR-EXISTING-ADMIN-AUTH-USER-UUID','admin')
   on conflict(user_id) do update set role='admin';
   ```

5. Configure your local `.env.local` using `.env.example`:

   ```env
   VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
   VITE_SUPABASE_ANON_KEY=YOUR-PUBLISHABLE-ANON-KEY
   VITE_CONTACT_WHATSAPP=91YOURBUSINESSMOBILENUMBER
   ```

   Do not use a Supabase **service_role** secret in any VITE variable; browser `VITE_` variables are public. Do not commit `.env.local` to Git.

6. Run:

   ```bash
   npm ci
   npm run dev
   ```

7. Go to `/admin`, sign in using the existing admin account, open **Employees** and register the first employee. Their `EMP0001` code is generated by the database.
8. To allow an employee to log in: first create/invite their account in Supabase **Authentication → Users**, then paste the account's Auth user UUID into the employee edit form (admin only). The SQL trigger automatically creates their CRM membership. The employee then logs in through `/admin` with Supabase email/password and gets the staff workspace. **Employee ID alone is not a secure login.**
9. Assign a lead in Customer Leads → Manage. The employee can now see that lead on their workspace.

## What this does **not** do automatically

- Does not create users or passwords from the browser. You must create Auth users through Supabase admin tools.
- Does not auto-assign fresh enquiries; admins manually assign them on the Manage Lead screen.
- Does not send WhatsApp messages, SMS, emails or OS push reminders automatically. WhatsApp links open a prepared conversation. In-app follow-ups work while a user accesses the CRM.
- Does not automatically mark inventory `Reserved` or `Sold` when a booking is made; update the corresponding property record explicitly.
- Does not implement a separate customer login portal, commission payout ledger or document-signing workflow.
- Does not verify existing `properties`, `property_images`, `lead_activity` or other legacy policies. Audit their RLS before client deployment.

## Security + compatibility notes

- This migration uses **additive** tables plus an `assigned_employee_uuid` column on existing `leads`.
- The SQL includes restrictive SELECT/UPDATE/DELETE policies on `leads`. It intentionally leaves your existing public INSERT policy intact so the public Contact form can still submit. **Review existing permissive policies and what unauthenticated users may INSERT** before production. A hardened server-side enquiry intake with rate limiting is recommended.
- Existing leads with only legacy `employee_name`/`employee_id` fields stay visible to managers. They will not show to an employee until `assigned_employee_uuid` is populated.
- The employee photo bucket is **private** and uses temporary signed URLs.
- For a real client, verify backups, all privacy policies, production domain, privacy notice, spam protection, email deliverability, RLS, mobile flows and admin role boundaries.
